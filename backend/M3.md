# M3 runbook — normalization, deterministic matcher and reviewer roles

M3 replaces the substring matcher from M2 with deterministic normalization and
fuzzy scoring, adds reviewer-learned aliases and low-confidence suggestions, and
enforces the reviewer role on the review queue. Firebase still owns credentials;
Postgres still owns `user` / `reviewer` / `admin` roles. No AI model categorizes,
ranks or decides a match.

## Components

| Component | Location | Purpose |
|---|---|---|
| Matcher | `app/services/matcher.py` | normalization, hard gates, rapidfuzz scoring, aliases, optional pgvector candidate recall |
| Migration | `alembic/versions/0003_matching.py` | `product_aliases`, suggestion columns on staging, opportunistic `product_embeddings` |
| Pipeline | `app/services/ingestion.py` | uses `match_listing()`, preserves manual decisions, stores suggestions |
| Review API | `app/api/v1/review.py`, `app/api/deps.py` | reviewer/admin review endpoints; health and manual scrape stay admin-only |
| Tests | `tests/test_matcher.py`, `tests/test_review_api.py`, `tests/test_ingestion.py` | normalization, false-positive gates, alias learning, RBAC, decision preservation |

## Configuration

`backend/.env.example` adds:

```dotenv
MATCH_AUTO_MIN=0.88       # >= this score publishes an auto-matched offer
MATCH_REVIEW_MIN=0.72     # >= this score stores a reviewer suggestion
MATCH_VECTOR_DIMS=256     # deterministic hashed-trigram vector size
```

`rapidfuzz` is locked in `uv.lock` and installed via `uv sync`.

## How matching works

1. Titles are NFKD-normalized, Arabic-Indic digits are converted, trademark
   symbols and punctuation are stripped, marketing words (`geforce`, `gaming`,
   `tray`, `oc`, …) are removed, and packed codes (`RTX4060`) are split.
2. Hard gates reject a candidate before fuzzy scoring:
   - **bundle** titles (`-BUILD-`, `combo`, `powered by`) are never auto-matched;
   - **model identity** must overlap, with suffixes preserved (`7600x3d` ≠ `7600`,
     `4060ti` ≠ `4060`, `4070tisuper` ≠ `4070super`, `tx750` ≠ `gx750`);
   - **capacity** must agree when both sides state one (`16GB` ≠ `64GB`);
   - **brand** and **inferred category** must agree when known.
3. Remaining candidates are scored with `WRatio`, `token_set_ratio`,
   `token_sort_ratio` and exact-containment boosts. Generic slugs without an
   identity token cannot decide a SKU. Learned aliases are curated mappings and
   are allowed to match directly.
4. If pgvector is available, deterministic hashed-trigram vectors provide up to
   eight extra candidates. Their score is capped below `MATCH_AUTO_MIN`, so
   vectors can only propose review suggestions, never publish an offer alone.
5. Score ≥ `MATCH_AUTO_MIN` → `auto_matched` and eligible for `recompute_offers()`.
   Score ≥ `MATCH_REVIEW_MIN` → `unmatched` with `suggested_product_id`,
   `suggestion_confidence` and `suggestion_reason` in the review queue.
   Lower scores are plain `unmatched`.
6. A reviewer's `matched` or `rejected` decision survives later scrapes of the
   same `(merchant_id, external_id)`. Approving a match also learns a normalized
   alias for future listings.

## Roles

| Endpoint | Access |
|---|---|
| `GET /api/v1/admin/review/listings`, `POST …/match`, `POST …/reject` | reviewer or admin |
| `GET /api/v1/admin/scrapers/health`, `POST /api/v1/admin/scrape/run` | admin only |
| Public catalog, builder and price-history APIs | any user |

## Review API additions

`ReviewListing` now includes `suggested_product_id`, `suggestion_confidence` and
`suggestion_reason`. Example with a reviewer token:

```bash
curl "http://localhost:8000/api/v1/admin/review/listings?status=unmatched" \
  -H "Authorization: Bearer $REVIEWER_TOKEN"

curl -X POST http://localhost:8000/api/v1/admin/review/listings/123/match \
  -H "Authorization: Bearer $REVIEWER_TOKEN" -H 'Content-Type: application/json' \
  -d '{"product_id": 7}'
```

A plain `user` token receives 403. The match response clears the suggestion
fields; the alias is stored with `source="manual"` and the reviewer's user id.

## Known limitations

- The M2 exit target of ≥90% auto-match applies to listings that correspond to a
  curated catalog product. The live broad searches return 1,056 listings while
  the development catalog has only 15 SKUs; most unmatched titles are genuinely
  out-of-catalog (7600X, 4070 Ti, 96GB RAM kits, H7 Flow, other board vendors) or
  bundles. Raw auto-match rate on those pages is 14/1,056. Raising it further is
  a manual catalog-curation task, not a threshold change: lowering thresholds
  would publish wrong prices.
- pgvector and Meilisearch are now verified in the full Docker stack (above);
  the local vanilla-Postgres smoke still intentionally skips embeddings when
  `vector` is absent.
- Web Bot Auth for Compumarts and real Firebase token verification remain
  unverified here, as noted in `M2.md`. Scheduled arq cron *firing* was not
  waited for, though registration and on-demand worker execution are verified.
