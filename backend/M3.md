# M3 runbook — normalization, deterministic matcher and reviewer roles

M3 replaces the substring matcher from M2 with deterministic normalization and
fuzzy scoring, adds reviewer-learned aliases and low-confidence suggestions, and
enforces the reviewer role on the review queue. Firebase still owns credentials;
Postgres still owns `user` / `reviewer` / `admin` roles. No AI model categorizes,
ranks or decides a match.

## Components

| Component | Location | Purpose |
|---|---|---|
| Matcher | `app/services/matcher.py` | normalization, hard gates, rapidfuzz scoring, aliases, optional pgvector candidate recall |
| Migration | `alembic/versions/0003_matching.py` | `product_aliases`, suggestion columns on staging, opportunistic `product_embeddings` |
| Pipeline | `app/services/ingestion.py` | uses `match_listing()`, preserves manual decisions, stores suggestions |
| Review API | `app/api/v1/review.py`, `app/api/deps.py` | reviewer/admin review endpoints; health and manual scrape stay admin-only |
| Tests | `tests/test_matcher.py`, `tests/test_review_api.py`, `tests/test_ingestion.py` | normalization, false-positive gates, alias learning, RBAC, decision preservation |

## Configuration

`backend/.env.example` adds:

```dotenv
MATCH_AUTO_MIN=0.88       # >= this score publishes an auto-matched offer
MATCH_REVIEW_MIN=0.72     # >= this score stores a reviewer suggestion
MATCH_VECTOR_DIMS=256     # deterministic hashed-trigram vector size
```

`rapidfuzz` is locked in `uv.lock` and installed via `uv sync`.

## How matching works

1. Titles are NFKD-normalized, Arabic-Indic digits are converted, trademark
   symbols and punctuation are stripped, marketing words (`geforce`, `gaming`,
   `tray`, `oc`, …) are removed, and packed codes (`RTX4060`) are split.
2. Hard gates reject a candidate before fuzzy scoring:
   - **bundle** titles (`-BUILD-`, `combo`, `powered by`) are never auto-matched;
   - **model identity** must overlap, with suffixes preserved (`7600x3d` ≠ `7600`,
     `4060ti` ≠ `4060`, `4070tisuper` ≠ `4070super`, `tx750` ≠ `gx750`);
   - **capacity** must agree when both sides state one (`16GB` ≠ `64GB`);
   - **brand** and **inferred category** must agree when known. Inference now
     covers all tracked categories, including `prebuilt`; component/bundle
     phrases such as "desktop RAM" and "case + PSU combo" are excluded from
     prebuilt so they cannot create false gates.
3. Remaining candidates are scored with `WRatio`, `token_set_ratio`,
   `token_sort_ratio` and exact-containment boosts. Generic slugs without an
   identity token cannot decide a SKU. Learned aliases are curated mappings and
   are allowed to match directly.
4. If pgvector is available, deterministic hashed-trigram vectors provide up to
   eight extra candidates. Their score is capped below `MATCH_AUTO_MIN`, so
   vectors can only propose review suggestions, never publish an offer alone.
5. Score ≥ `MATCH_AUTO_MIN` → `auto_matched` and eligible for `recompute_offers()`.
   Score ≥ `MATCH_REVIEW_MIN` → `unmatched` with `suggested_product_id`,
   `suggestion_confidence` and `suggestion_reason` in the review queue.
   Lower scores are plain `unmatched`.
6. A reviewer's `matched` or `rejected` decision survives later scrapes of the
   same `(merchant_id, external_id)`. Approving a match also learns a normalized
   alias for future listings.

## Roles

| Endpoint | Access |
|---|---|
| `GET /api/v1/admin/review/listings`, `POST …/match`, `POST …/reject` | reviewer or admin |
| `GET /api/v1/admin/scrapers/health`, `POST /api/v1/admin/scrape/run` | admin only |
| Public catalog, builder and price-history APIs | any user |

## Review API additions

`ReviewListing` now includes `suggested_product_id`, `suggestion_confidence` and
`suggestion_reason`. Example with a reviewer token:

```bash
curl "http://localhost:8000/api/v1/admin/review/listings?status=unmatched" \
  -H "Authorization: Bearer $REVIEWER_TOKEN"

curl -X POST http://localhost:8000/api/v1/admin/review/listings/123/match \
  -H "Authorization: Bearer $REVIEWER_TOKEN" -H 'Content-Type: application/json' \
  -d '{"product_id": 7}'
```

A plain `user` token receives 403. The match response clears the suggestion
fields; the alias is stored with `source="manual"` and the reviewer's user id.

## Real Firebase verification

Unit tests override `decode_token`, so they prove RBAC logic but not Firebase
itself. `tests/test_firebase_verification.py` covers the real code path with a
mocked verifier; the script below performs end-to-end verification when
credentials are available. Firebase owns credentials; Postgres still owns roles.

Obtain a fresh ID token from the signed-in Flutter app
(`FirebaseAuth.instance.currentUser!.getIdToken()`), then:

```bash
cd backend
export FIREBASE_PROJECT_ID=your-project-id
export FIREBASE_CREDENTIALS=/secure/path/service-account.json  # or GOOGLE_APPLICATION_CREDENTIALS
export FIREBASE_ID_TOKEN='eyJ...'
uv run python -m scripts.verify_firebase_auth --expected-uid '<firebase uid>'
```

The script prints `uid`, `email`, `email_verified`, `aud`, `iss`, `iat` and `exp`,
and exits non-zero on an invalid/expired token or uid mismatch. `decode_token`
uses `firebase_admin.auth.verify_id_token(..., check_revoked=False)`;
`get_current_user` then resolves the uid to a local `User` row and RBAC reads the
Postgres role.

For an offline-but-real Firebase check, run the Auth emulator and let the script
create a temporary user, sign in through the emulator REST API, and verify the
emitted token through the same backend code path:

```bash
firebase emulators:start --only auth --project demo-tagme3a
cd backend
FIREBASE_PROJECT_ID=demo-tagme3a \
  uv run python -m scripts.verify_firebase_auth --emulator-host 127.0.0.1:9099
```

If you have the Web API key and service account but no token handy, use the
live smoke mode. It creates a temporary user in the real project, signs it in,
verifies the token through `decode_token()`, and deletes the user in a `finally`
block:

```bash
cd backend
export FIREBASE_PROJECT_ID=tagme3a
export FIREBASE_CREDENTIALS=/secure/path/service-account.json
export FIREBASE_WEB_API_KEY='<Firebase Console → Project settings → Web API key>'
unset FIREBASE_AUTH_EMULATOR_HOST
uv run python -m scripts.verify_firebase_auth --create-test-user
```

`app.core.security._get_firebase_app()` skips service-account loading when
`FIREBASE_AUTH_EMULATOR_HOST` is set. Both paths were verified on 2026-11-27:
the emulator run with `firebase-tools` 15.37.0 (`aud=demo-tagme3a`), and the
live-project smoke against `tagme3a` (`aud=tagme3a`,
`iss=https://securetoken.google.com/tagme3a`). The tmp user was deleted after
each run. Checking a specific existing user still needs that user's fresh ID
token or password.

## Known limitations

- The M2 exit target of ≥90% auto-match applies to listings that correspond to a
  curated catalog product. The four-merchant pages return 3,064 listings while the
  development catalog has only 15 SKUs; most unmatched titles are genuinely
  out-of-catalog (7600X, 4070 Ti, 8000 MT/s RAM kits, H7 Flow, other board vendors,
  2B's laptop-heavy catalog) or bundles. Raw auto-match rate is 22/3,064 (2B: 0/267).
  Raising it further is a manual catalog-curation task, not a threshold change:
  lowering thresholds would publish wrong prices. A broad deterministic candidate
  CSV (`data/curated_skus_all.csv`, 2,998 rows across all 11 categories) is now
  generated from robots-allowed merchant pages for owner review; import and
  recompute are still pending, so the 22/3,064 figure has not changed yet.
- pgvector and Meilisearch are now verified in the full Docker stack (above);
  the local vanilla-Postgres smoke still intentionally skips embeddings when
  `vector` is absent.
- 2B is limited to robots-allowed category HTML with the identifying bot UA.
  Web Bot Auth is published and verified locally (see `M2.md`), but production
  deployments still need the private key in their secret store. Firebase
  verification passed against both the Auth emulator and the live `tagme3a`
  project; live cron firing with a worker and Redis remains unverified. The
  repo-side harnesses and verification steps are documented below and in
  `M2.md` / `OPS_WEBHOOKS.md`. Attackers cannot bypass RBAC by
  sending a role claim: `get_current_admin` / `get_current_reviewer` read the
  role from Postgres, not from Firebase custom claims.
